# SEED 한일 고령화–부동산 연구: 일본 데이터

이 문서는 **확정 작업**(계획 작성 → 사용자 승인 → 실제 변경)만 기록한다. 논의 중이거나 미실행인 항목은 적지 않는다.

## 1. 개요

### 1.1 이 데이터가 무엇인가
`Population2/`의 17개 파일은 일본 総務省이 매년 공표하는 「住民基本台帳に基づく人口、人口動態及び世帯数調査」 중
**「市区町村別 年齢階級別 人口（日本人住民）」** 표이다. 住民基本台帳은 한국의 주민등록에 해당하는 공적 장부이며,
이 표는 거기에 등록된 **일본 국적 주민**을 시구정촌별 · 5세 단위 연령별 · 성별로 집계한 것이다.

- 기간: 2010~2026, 연 1회, 17개 파일
- 기준일: 2013년까지 **3월 31일**, 2014년부터 **1월 1일** (総務省의 집계 기준일 변경)
- 출처: e-Stat (政府統計の総合窓口) → 住民基本台帳に基づく人口、人口動態及び世帯数調査 → 年次 → 【日本人住民】市区町村別年齢別人口
- 다운로드: 사용자가 직접 수행 (2026-10-03)

### 1.2 연구에서의 역할
가설 H1 "고령화율 상승은 부동산 가격을 낮춘다", H2 "그 효과의 크기를 한일 간 비교"에서
이 파일들은 **일본 쪽 독립변수(연령별 인구구조)의 유일한 원천**이다.
여기서 65세 이상 비중(고령화율), 0~14세 비중, 청년층 비중 등을 시구정촌 × 연도 단위로 만들고,
reinfolib 실거래가 · 지가공시(종속변수)와 시구정촌 코드로 결합한다.
최종적으로 과소지역(過疎地域) 시정촌만 걸러 한국의 인구감소지역 시군구 데이터와 대응시킨다.

### 1.3 왜 【日本人住民】 시리즈인가
처음에는 외국인을 포함한 【総計】 파일(2014~2026, `Japen_Population/`)을 받았다.
그러나 2012년 이전 자료는 외국인이 住民基本台帳에 등록되지 않던 시기(2012-07-09 법 개정 이전)라 내국인만 집계돼 있다.
관측 기간을 2010년까지 늘리면서 전 기간을 같은 기준으로 맞추기 위해 **내국인만 집계한 【日本人住民】 시리즈로 전부 교체**했다.
시작 연도를 2010년으로 잡은 이유는 1999~2010년의 대규모 시정촌 합병(平成の大合併)이 2010년 3월에 끝나
그 이후 행정구역 코드가 안정적이기 때문이다.

### 1.4 한계
- 시구정촌이 최소 단위다. 그보다 작은 단위(町丁目)로는 쪼갤 수 없다.
- 2010~2014년은 80세 이상이 한 구간이다. 85세 이상 세분화는 2015년부터만 가능하다.
- 2013→2014 사이는 기준일 변경 때문에 9개월 간격이다.

## 3. 1단계: 원본 17개를 같은 양식의 CSV 17개로 (확정, 2026-10-06)

### 3.1 실제로 바꾼 것과 근거

| # | 바꾼 것 | 근거 |
|---|---|---|
| ① | 연도·기준일을 **파일 첫 칸의 제목**(`平成26年1月1日住民基本台帳…（日本人住民）`)에서 읽음. 2013년 이후 파일에 `日本人住民` 표기가 없으면 스크립트가 멈춤 | 원본 파일명이 제각각(`1608nanen.xls`, `【日本人住民】…26nsnen.xlsx` 등)이라 파일명을 믿을 수 없음. 시리즈 혼입 방지 |
| ② | `団体コード`가 6자리 숫자인 행만 남김. 제목 행, 헤더(2~3줄), 전국 합계 행, 하단 주석 행 제거 | 헤더 줄 수가 연도마다 달라(2010~2020: 2줄, 2021~: 3줄) 위치가 아니라 내용으로 걸러야 함 |
| ③ | 연령 컬럼 이름을 `age_0_4` 식으로 통일. 원본 라벨에서 숫자만 뽑아 구간 하한으로 판별 | `0～4歳` / `5～9` / `0歳～4歳` / `80歳以上` 등 표기가 연도마다 다름 |

| ⑥ | 計/男/女 3행 → 지역당 1행. 남자는 `_m`, 여자는 `_f` 접미사 | 지역당 1행이어야 다른 데이터와 결합이 쉬움. 성별 정보는 버리지 않음 |

| ⑧ | 파일명 `jp_pop_YYYY.csv` (YYYY는 ①에서 읽은 값). 17개를 이어 붙이지 않고 연도별로 저장 | 파일명 통일. 연도별 파일 유지는 사용자 결정 |

### 3.4 `muni_code` 읽는 법
全国地方公共団体コード. 한국의 행정표준코드(시군구 5자리)에 해당한다.

| 자리 | 뜻 | 예 (`01101` 札幌市中央区) |
|---|---|---|
| 1~2 | 도도부현 (01 北海道 … 13 東京都 … 47 沖縄県) | `01` |
| 3~5 | 도도부현 안의 시구정촌 | `101` |

3~5자리 범위로 행 종류를 알 수 있다: `000` 도도부현 자체 / `100` 정령시 합계 / `101`~`199` 정령시의 구 / `201`~ 일반 시 / `300`~ 郡 소계와 그 아래 町村.
reinfolib 실거래가 · 지가공시 · 過疎地域 목록은 모두 이 5자리를 쓴다. 6자리의 마지막 숫자는 검증숫자(check digit)로 정보가 없다.

- 도쿄 섬 지역 이름이 2010~2015에만 접두어를 포함한다 (`三宅島　三宅村`, `八丈島　八丈町`; 전각 공백). 2016부터 `三宅村`, `八丈町`. 코드로 매칭하므로 결합에는 영향 없음. 이름을 쓸 일이 있으면 주의.
- 2026년 최대 오차 0.18%는 山口県 阿武町(`35502`)와 그 郡 소계 阿武郡(`35500`). 연령불상자 5명 차이. 이 郡은 町이 하나뿐이라 두 행 값이 같다. **2단계에서 郡 소계 행을 뺄 때 코드 범위로 걸러야 이런 1町 郡이 중복 집계되지 않는다.**

## 4. 2단계: 행 종류 라벨 붙이기 (확정, 2026-10-06)

### 4.1 무엇을 했나
1단계 파일 17개의 **모든 행을 그대로 두고**, 각 행이 어떤 종류인지(`row_type`)와 소속 시정촌 코드(`city_code`)를 컬럼으로 추가했다.
**행은 하나도 지우지 않았다.** 사용자 결정: 정보값을 날리지 않고 전부 저장하며, 어느 단위로 거를지는 분석 때 `row_type`으로 고른다.

원본 파일 한 장 안에는 서로 다른 단위의 행이 섞여 있다. 도도부현 합계, 정령시 합계, 郡 소계가 시구정촌 행과 함께 있어서
그대로 합치면 같은 인구가 여러 번 더해진다. 그래서 어떤 행이 합계이고 어떤 행이 분석 단위인지 라벨이 필요했다.

### 4.2 일본 행정구역 포함 관계와 한국 대응

```text
도도부현 (都道府県)                     한국: 시·도              row_type = pref        예: 01000 北海道
│  ※ 아래 전부를 더한 합계 행
├── 정령시 (政令指定都市)               한국: 특례시             row_type = city_agg    예: 01100 札幌市
│   │  ※ 아래 구를 더한 합계 행
│   └── 구 (行政区, 자치권 없음)         한국: 일반구             row_type = ward        예: 01101 札幌市中央区
├── 도쿄 특별구 (特別区, 자치권 있음)   한국: 서울 자치구        row_type = special_ward 예: 13101 千代田区
├── 일반 시 (市)                        한국: 시                 row_type = city        예: 01202 函館市
└── 군 (郡, 행정단위 아님)              한국: 대응 없음          row_type = gun_agg     예: 02320 西津軽郡
    │  ※ 아래 町·村을 더한 합계 행. 주소 표기용 묶음일 뿐
    ├── 町                              한국: 읍 (단, 일본에선 기초자치단체)  row_type = town     예: 35502 阿武町
    └── 村                              한국: 면 (단, 일본에선 기초자치단체)  row_type = village  예: 01695 色丹村
```

그 밖에 `13360 島しょ`(도쿄 섬 지역 町·村의 합계, `island_agg`)와 인구 0인 북방영토 6개 촌(`zero_pop`)이 있다.

핵심 차이: **한국의 군은 기초자치단체지만 일본의 郡은 이름 묶음일 뿐이다.** 일본에서 기초자치단체는 郡 아래의 町·村이다.
따라서 한국 시군구에 대응하는 일본 단위는 **시정촌(市·町·村) + 도쿄 23구**이고, 한국 "군"에 대응하는 것은 일본 郡이 아니라 町·村이다.

| 한국 | 일본 | row_type |
|---|---|---|
| 시·도 (17) | 도도부현 (47) | `pref` |
| 시·군·구 (226, 기초자치단체) | 시정촌 (약 1,720) + 도쿄 23구 | `city_agg` + `special_ward` + `city` + `town` + `village` |
| 일반구 (자치권 없음) | 정령시의 구 (자치권 없음) | `ward` |
| 읍·면 | 町·村 | `town`, `village` |

### 4.3 판별 규칙 (코드 3~5자리 범위 + 이름 끝글자)

| row_type | 규칙 | 처리 (분석 시) |
|---|---|---|
| `zero_pop` | `pop_total == 0` (북방영토 6개 촌, 전 연도) | 제외 |
| `pref` | 코드 3~5자리 `000` | 합계 행, 제외 |
| `city_agg` | `100`~`199` 이고 이름 끝 `市` | 정령시 합계. 시정촌 단위면 사용, 시구정촌 단위면 제외 |
| `special_ward` | `100`~`199`, 도도부현 `13` | 도쿄 23구. 항상 사용 |
| `ward` | `100`~`199` 이고 이름 끝 `区`, 도도부현 `13` 제외 | 정령시의 구. 시구정촌 단위면 사용 |
| `city` | `200`~`299` | 항상 사용 |
| `gun_agg` | `300` 이상이고 이름 끝 `郡` | 郡 소계, 제외 |
| `island_agg` | `13360 島しょ` | 합계 행, 제외 |
| `town` / `village` | `300` 이상이고 이름 끝 `町` / `村` | 항상 사용 |

**코드만으로는 판별할 수 없다.** 처음에는 "코드 끝이 `00`이면 郡 소계, `100`이면 정령시 합계"로 제안했으나 실제 데이터에서 틀렸다.
- 郡 소계 코드는 `02320 西津軽郡`처럼 `20/40/60/80`으로도 끝난다. 반대로 `01400 虻田郡倶知安町`은 `00`으로 끝나지만 町이다.
- 정령시 합계는 `14130 川崎市`, `14150 相模原市`, `27140 堺市`, `22130 浜松市`, `40130 福岡市`처럼 `100`이 아닌 것이 5개 있다.
- "`1xx`에서 끝자리 `0`이면 합계"도 틀렸다. `01110 札幌市清田区`, `13110 目黒区`, `13120 練馬区`, `22140 浜松市天竜区` 등 끝자리 `0`인 구가 10개 있다.
- 町이 하나뿐인 郡(`35500 阿武郡` / `35502 阿武町`)은 두 행의 값이 같지만 이름 끝글자로 구분된다.
- 이름 끝글자 규칙은 2010~2026 전체 38,721행에서 판별 불가 0건이었다. 郡 이름에 村이 들어간 경우(`東村山郡` 등 4건)도 끝글자가 郡이라 문제없다.
- **北海道(01)는 원본에 郡 소계 행이 없다.** 町村 144개가 어느 `gun_agg`에도 속하지 않는다. 다른 46개 도도부현은 모두 郡 소계가 있다. (외부 검증 2026-10-06)

### 4.4 추가 컬럼 (`muni` 바로 다음에 삽입, 총 77컬럼)

| 컬럼 | 뜻 | `ward` 행 | 단위 행 (`special_ward`/`city`/`town`/`village`) | 합계 행 |
|---|---|---|---|---|
| `row_type` | 행 종류 (위 표) | `ward` | 각자 | 각자 |
| `city_code` | 시정촌 단위 코드 | **소속 정령시 합계 코드** (예: `01101` → `01100`) | 자기 `muni_code` | 빈칸 |

`city_code`가 필요한 이유: 정령시의 구는 자기 코드(`01101`)와 소속 시 코드(`01100`)가 다르고, 소속 정보가 이름(`札幌市中央区`)에만 있다.
구 단위로 분석하다가 시정촌 단위로 묶거나 과소지역 목록(시정촌 코드)과 결합할 때 `city_code`로 묶으면 된다.
구의 소속 시는 "같은 도도부현 안에서 구 이름이 정령시 이름으로 시작하는가"로 판별했다.

### 4.5 분석 단위별 거르는 법

두 경우 모두 `pref`, `gun_agg`, `island_agg`, `zero_pop`은 뺀다.

## 5. 3단계: 2026년 코드 기준으로 통일하여 한 파일로 (확정, 2026-10-06)

### 5.1 무엇을 했나

| 2 기록용 | `output/jp_pop_2026basis_with_std.csv` | 출력 1과 행·순서·값이 완전히 같고, 각 행이 원래 어떤 행이었는지 std 4컬럼을 붙인 것 | 32,104 × 80 |

**데이터는 아무것도 삭제되지 않았다.** 출력 3의 102행은 원본 엑셀, 2단계 파일, 출력 3 세 곳에 그대로 있다.

### 5.2 왜 2026년 경계인가, 그리고 세 도시의 한계
- 합병은 되돌릴 수 없다. 2010년 경계를 기준으로 하면 합병 후 시를 쪼개야 하는데 불가능하다. 그래서 통상적 방법대로 **최신(2026년) 경계**를 기준으로 삼았다.
- 사용자 결정: 분석 단위는 **시구정촌(정령시는 구 단위)**. 시정촌 단위로 묶자는 제안은 "최대한 작은 단위" 목적에 맞지 않아 채택하지 않았다.
- 그런데 相模原市(2011 정령시 승격), 熊本市(2013 승격), 浜松市(2024 구 개편) 세 곳은 **2026년의 구가 옛 연도에 존재하지 않는다.** 2010년 熊本市 1행을 2026년 5개 구로 쪼갤 방법은 없다.
  이 세 도시에 대해서는 "2026년 구 단위 / 연도 안 섞기 / 17년 전부 채우기" 세 가지를 동시에 만족할 수 없어서, 사용자가 **17년 채우기를 포기하는 쪽**을 택했다.
  즉 2026년 구 구조를 그대로 두고, 구가 없던 연도의 시 행(과 浜松의 옛 7구 행)은 출력 3으로 분리했다.
  세 도시 모두 정령시라 과소지역이 아니므로 최종 데이터에는 영향이 없다.

### 5.3 절차 (`scripts/standardize_jp_population.py`)
1. 2단계 파일 17개를 세로로 이어 붙임 (38,721행)
2. 단위 행만 선택: `row_type ∈ {ward, special_ward, city, town, village}`. 합계 행(`pref`, `city_agg`, `gun_agg`, `island_agg`)과 `zero_pop`은 제외 (32,206행)
3. 대응표로 각 행의 2026년 코드를 정함. 대응표에 없는 행은 자기 코드 그대로
4. `std_note`가 `C_designated_city` 또는 `D_ward_reorg`인 행(102행)은 출력 3으로 분리
5. 나머지를 `(year, 2026년 코드)`로 묶어 인구 69개 컬럼을 더함 (`min_count=1`: 2010~2014의 `age_80_84`~`age_100p` NA가 0으로 바뀌지 않도록) → 출력 1
6. 묶은 행의 `pref`·`muni`·`row_type`·`city_code`는 **2026년 파일을 참조표로 코드 결합** (그룹의 첫 행에서 가져오면 합병된 町 이름이 붙을 수 있음)
7. 같은 행에 std 4컬럼을 붙임 → 출력 2

### 5.7 자동 검사 (전부 통과, 2026-10-06)
1. 대응표 38행 모두: `old_code`가 `last_year_old`까지의 데이터에 있고 그 이름이 `old_name`과 일치. A·B·C·D는 다음 해에 `old_code` 없음, E는 다음 해에 `new_name`으로 바뀜. `new_code`는 2026 파일에 있고 이름이 `new_name`
2. 출력 1·2: 행 수·순서 같고 공통 76컬럼의 값이 전부 같음
3. 출력 1 `(year, muni_code)` 중복 없음
4. **균형 검사**: 5.6의 비는 자리를 제외하면 **17개 연도의 `muni_code` 집합이 2026년 단위 행 집합과 완전히 같음**. 통과하면 누락된 행정구역 변경이 없다는 뜻
5. 시정촌 단위(`city_code`, 출력 1 + 출력 3): 17개 연도 집합 동일
6. 연도별 합 (출력 1 + 출력 3) = 그 해 47개 도도부현 행의 합 — 스크립트는 `pop_total`로 검사하고, 외부 검증(2026-10-06)에서 **인구 69컬럼 전부** 일치 확인. 묶어 더하는 과정에서 누락·중복 없음
7. B의 흡수한 시 6곳: 17년간 `pop_total` 전년 대비 변동 10% 미만 (합병 전후 급변 없음)
8. 출력 2: `n_orig ≥ 2`인 행은 전부 `B_merged_into`, `orig_code` 개수 = `n_orig`
9. 출력 3: 102행, `std_note`는 C 4행 / D 98행

연도별 출력 1 행 수: 2010 1,881 / 2011~2012 1,884 / 2013~2023 1,889 / 2024~2026 1,892. 차이는 전부 5.6의 비는 자리 때문이다.

## 6. 5단계: 과소지역 필터 (확정, 2026-10-06)

4단계(파생 변수: 비중·청년 정의)는 한국 쪽 정의에 맞춰야 하므로 **한국 데이터가 정해진 뒤**로 미뤘다. 5세 단위 원자료가 그대로 있어 정의만 정해지면 바로 만들 수 있다.

### 6.1 무엇을 했나
3단계 분석용 패널(`jp_pop_2026basis.csv`)에서 **과소지역 시정촌만** 골라낸 파일을 만들었다.
기본 파일 (a)는 시정촌 전체가 과소지역인 727곳, 참고 파일 (b)는 목록 885곳 전부다. 사용자 결정: 패널에 과소구분 컬럼은 넣지 않고, 구분은 매칭표에만 남긴다.

| 출력 | 경로 | 내용 | 행 × 열 |
|---|---|---|---|
| 매칭표 | `output/kaso_match.csv` | 885곳 각각에 우리 코드를 붙인 표. 열: `no, pref, kaso_name, kaso_kind, partial_area, muni_code, muni, row_type`. **과소구분(`kaso_kind`)은 여기에만 있다** | 885 × 8 |

### 6.2 과소지역 목록의 출처와 성격
- 파일: `Kaso(과소지역)/000807167.xlsx`. 総務省 過疎対策 페이지(https://www.soumu.go.jp/main_sosiki/jichi_gyousei/c-gyousei/2001/kaso/kasomain0.htm)의 「過疎地域市町村等一覧(令和4年4月1日現在)」. 사용자가 직접 내려받아 넣음 (2026-10-06). PDF판도 같은 페이지에 있다.
- 근거 법: 2021년 시행 「過疎地域の持続的発展の支援に関する特別措置法」. 2020년 国勢調査 결과를 반영해 확정된 전국 지정 목록이며(엑셀 제목에 「令和２年国勢調査結果に基づき異動のある市町村を含む」 명시), 이후 공식 자료에서도 885곳 체계가 유지되고 있다.
- 시트 3개: `過疎地域数`(도도부현별 집계), `市町村数`(**본체 885곳**, 번호 1~885), `卒業`(구법에서 과소였다가 요건을 벗어난 41곳. 시트에는 45행이 있으나 4곳은 취소선으로 2022-04-01에 다시 과소지역이 된 곳)
- **団体コード가 없다.** 都道府県名과 市町村名만 있어 이름으로 결합해야 한다.

세 구분 (외부 검증 2026-10-06에서 정리한 정의):

| 구분 | 곳 | 정의 |
|---|---|---|
| 全部過疎 | 713 | 현재 시정촌 **전체**가 과소지역 |
| 一部過疎 | 158 | 현재 시정촌 전체가 아니라, 합병 전 구 시정촌 등 법에서 과소지역으로 간주되는 **특정 구역만** 과소지역인 시정촌. 어느 구 시정촌인지 파일의 `一部過疎について過疎地域とみなされる区域（旧市町村）` 열에 있다 (예: 函館市 → 戸井町、恵山町、椴法華村、南茅部町) |
| みなし過疎 | 14 | 법의 합병 관련 규정에 따라 현재 시정촌 **전체**가 과소지역으로 간주되는 시정촌 |

### 6.3 (a)를 기본으로 한 이유
우리 인구 데이터는 시정촌 단위라서 一部過疎 시의 "구 시정촌 구역"만 잘라낼 수 없다. 一部過疎를 넣으면 과소가 아닌 시 중심부 인구까지 통째로 들어간다.
全部過疎와 みなし過疎는 시정촌 전체가 과소지역이므로 단위가 맞고, 한국 인구감소지역이 시군구 전체 단위로 지정되는 것과도 대응이 깔끔하다.
一部過疎를 포함한 (b)는 참고용으로 남겼다.

### 6.4 이름 매칭 방법 (`scripts/filter_kaso.py`)
1. 우리 쪽 `muni`에서 郡 접두를 제거 (`雨竜郡幌加内町` → `幌加内町`). 목록에는 郡 이름이 없다
2. 양쪽 모두 `ケ`(큰 글자) → `ヶ`(작은 글자)로 통일
3. `(pref, 이름)`으로 2026년 행과 결합

郡 접두 제거만으로 882/885곳이 붙고, 남은 3곳은 전부 `ケ`/`ヶ` 표기 차이였다:
`青森県 鰺ケ沢町 ↔ 西津軽郡鰺ヶ沢町`, `宮城県 七ケ宿町 ↔ 刈田郡七ヶ宿町`, `東京都 青ケ島村 ↔ 青ヶ島村`.

## 7. ③ 지가공시(地価公示): 지점 추출 → 시정촌×연도 집계 → 과소 패널 결합 (확정, 2026-10-06)

### 7.1 이 데이터가 무엇이고 왜 받았나
地価公示는 国土交通省이 매년 **1월 1일 기준**으로 전국 약 2만 6천 개 표준지(標準地)의 ㎡당 땅값을 평가해 3월에 공표하는 공식 땅값이다. 한국의 표준지 공시지가에 해당한다.
H1의 **종속변수 2**다. 종속변수 1인 실거래가(②, reinfolib)는 API 키 승인 대기 중이라(2026-10-06 신청) 먼저 ③을 만들었다.
과소지역은 거래가 드물어 실거래가가 연도별로 비는 곳이 많은 반면, 地価公示는 거래가 없어도 매년 같은 지점에 값이 있다.

### 7.2 출처와 파일
- 国土数値情報 다운로드 서비스 L01 地価公示: https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-L01-2025.html
- 연도별 전국 zip 17개 (`L01-10_GML.zip` … `L01-26_GML.zip`, 2010~2026). 주소 규칙 `https://nlftp.mlit.go.jp/ksj/gml/data/L01/L01-YY/L01-YY_GML.zip`.
  공식 페이지에서 Claude가 내려받아 `Chika(지가공시)/`에 넣었고(2026-10-06), 파일별 SHA256을 `SHA256SUMS.txt`에 기록했다. 같은 페이지에서 직접 받아 해시를 비교하면 동일 파일임을 확인할 수 있다.
- zip 안에는 CSV가 없다. GML(.xml), Shapefile(.shp/.dbf), 2018년 이후는 GeoJSON이 들어 있다. **GML을 읽었다.** `.dbf`는 컬럼명이 `L01_001`… 번호뿐이고 연도마다 뜻이 밀리지만, GML은 항목이 `postedLandPrice`처럼 이름으로 적혀 있어 추측 없이 대응할 수 있다.
- 이용 조건: 国土数値情報 이용약관에 따라 출처 표기 「国土数値情報（地価公示データ）（国土交通省）」.

## 8. ② 실거래가(不動産取引価格情報): API 수집 → 거래 CSV → 시정촌×연도 집계 → 과소 분리 (확정, 2026-10-07)

### 8.1 이 데이터가 무엇이고 왜 받았나
国土交通省이 부동산 매매 당사자에게 설문해 모은 **실제 거래 가격**이다. 한국의 국토부 실거래가에 해당한다. H1의 **종속변수 1**이다.
거래 1건이 1행이고, 거래 시기는 분기 단위, 위치는 시정촌 + 동네(地区)까지만 공개된다(개인정보 보호로 지번·정확한 날짜 없음, 면적·가격은 반올림).

### 8.2 출처와 수집 방법
- 不動産情報ライブラリ(reinfolib) API `XIT001` 不動産価格（取引価格・成約価格）情報取得: https://www.reinfolib.mlit.go.jp/help/apiManual/xit001/
- 웹 화면의 일괄 다운로드가 2024년 사이트 개편으로 없어져, **공식 API 키를 신청**(2026-10-06 개인 명의, 조사·연구 목적)해 2026-10-07 승인받아 사용했다. 키는 Windows 사용자 환경변수 `REINFOLIB_API_KEY`에만 있고 이 저장소 어디에도 적지 않는다.
- 호출 범위: `year`=2010~2026 × `quarter`=1~4 × `area`=01~47 × `priceClassification=01`(取引価格만. 02 成約価格은 2021년 이후 별도 출처라 제외). 1초 간격, 응답 바이트를 그대로 `Reinfolib/raw/`에 저장(3,055개). 2026년 2~4분기는 미공개(서버가 「検索結果がありません」 반환)라 파일 없음.

### 8.3 ②-1 거래 CSV (`scripts/extract_torihiki_points.py`) → `output/torihiki_points/torihiki_YYYY.csv` 17개

### 8.4 ②-2 시정촌×연도 집계 (`scripts/build_torihiki_muni.py`) → `output/torihiki_muni.csv`
- **코드 통일이 필요 없었다.** reinfolib는 과거 거래를 이미 현재(2026년) 시정촌 코드로 바꿔 제공한다. 2024년에 신설된 浜松市中央区(`22138`)에 2010년 거래 1,501건이 붙어 있고, 西方町(`09321`)·相模原市 승격 전 코드(`14209`) 등 옛 코드는 0건이다. 3단계 대응표를 적용해도 바뀐 거래 0건. 모든 거래 코드가 2026년 인구 패널에 존재(검사 통과).
- `(year, muni_code)`로 묶어 집계:

| 열 | 뜻 |
|---|---|
| `n_trades` | 거래 건수 (전체) |
| `n_land`, `med_ppsqm_land` | 토지만 거래 건수, `price_per_sqm` 중앙값 |
| `n_landbldg`, `med_ppsqm_landbldg` | 토지+건물 |
| `n_condo`, `med_ppsqm_condo` | 중고 아파트 |
| `n_farm`, `med_ppsqm_farm` | 농지 |
| `n_forest`, `med_ppsqm_forest` | 임야 |
| `med_unit_land` | 토지만 거래의 원본 `UnitPrice` 중앙값 (계산값 `med_ppsqm_land`와 대조용) |

검사: 집계 건수 합 = 5,033,013 / 종류별 건수 합 = 전체 / `(year, muni_code)` 중복 없음. 결과 31,745행.

### 8.5 ②-3 과소지역 727곳만 → `output/torihiki_kaso.csv`
`과소지역_매칭/jp_pop_kaso.csv`와 **행 순서·`year`·`muni_code`가 같은** 727곳 × 17년 = 12,359행. 식별 6열(`year, muni_code, pref, muni, row_type, city_code`) + 위 12열. **인구와 합치지 않았다**(사용자 결정). 거래 없는 해는 `n_*`=0, 가격 빈칸.

커버리지 (지가공시 ③과 대조):

| 연도 | 거래 있는 과소지역 수 (727곳 중) | 거래 건수 |
|---|---|---|
| 2010~2025 | 712~719 | 30,187~37,458 |
| 2026 (1분기만) | 588 | 4,662 |

- 727곳 중 **569곳은 17년 전부 거래가 있고, 17년 내내 거래가 없는 곳은 1곳**뿐이다. 지가공시(299곳 지점 없음)보다 커버리지가 훨씬 넓다.
- 다만 과소지역 거래는 연간 시정촌당 중앙값 수십 건 수준이고, 종류별로 나누면 한 자리 수인 곳이 많다. 분석 시 `n_*`로 건수를 확인할 것.
- 가격은 반올림된 공개값이고, 토지+건물은 건물 가치가 섞여 있다.
